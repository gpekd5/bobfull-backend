# ADR 0005: 도메인 간 의존 경계와 조회 조합 원칙

- 상태: `Accepted`
- 작성일: `2026-08-03`
- 관련 Issue·PR: `#122`

## 배경

예약 준비·확정과 회차·합석 테이블 변경 정책 검증 서비스가 다른 도메인의 Repository, Entity,
상태 Enum과 내부 연결 경로를 직접 사용하고 있었다. 이 구조는 유스케이스 조율 책임과 저장 구조·상태
정책 소유를 함께 갖게 해, 각 도메인의 내부 변경이 소비 서비스로 전파될 수 있다.

반면 회차·테이블·식당·예약·결제를 한 번에 조합하는 읽기 기능까지 서비스별 호출로 분해하면 호출 수와
쿼리가 늘어 구현 복잡도와 성능이 나빠질 수 있다.

## 문제

쓰기·상태 변경·정책 검증 경계에서 다른 도메인의 내부 저장 구조와 활성 상태 정의를 직접 아는 의존을
줄이면서도, 기존의 비관적 락 순서, 트랜잭션 전파, 예외 계약과 좌석 정합성을 보존해야 한다.

## 고려한 대안

### 대안 A — 현재 직접 Repository 의존 유지

- 장점: 구현이 단순하고 파일 수가 적다.
- 단점: 다른 도메인의 저장 구조·상태 정책 변경이 소비 서비스로 전파된다.

### 대안 B — 모든 도메인 간 호출을 Service/Port로 분리

- 장점: 경계가 가장 엄격하다.
- 단점: 단순 CRUD와 조회에도 Port·Adapter가 과도하게 늘고 서비스 체인이 길어진다.

### 대안 C — 쓰기·정책 검증만 최소 Port, 복합 조회는 Query 전용 구조

- 장점: 변경 영향과 정책 소유권을 줄이면서 조회 성능과 구현 복잡도를 함께 고려할 수 있다.
- 단점: 쓰기와 조회에 서로 다른 경계 기준을 팀이 이해하고 일관되게 적용해야 한다.

## 결정

대안 C를 채택한다.

쓰기·상태 변경·도메인 정책 검증 서비스는 다른 도메인의 Repository, Entity, 내부 상태 Enum에 직접
의존하지 않는다. 소비 도메인이 유스케이스에 필요한 최소 Port와 불변 DTO/record를 정의하고, Adapter가
기존 Repository 및 내부 연결 구조를 캡슐화한다.

여러 도메인을 조합하는 조회는 서비스 체인을 늘리지 않고 전용 QueryRepository, Projection, Read Model을
사용할 수 있다. 같은 Aggregate 또는 명확한 부모–하위 자원 관계의 단순 존재·소유권 검증까지 Port로
일괄 강제하지 않는다.

## 선택 이유

예약 서비스는 예약 준비와 확정의 순서를 조율하지만 TimeSlot→SharedTable→Restaurant 연결 구조와 활성
예약 상태의 구현을 소유하지 않는다. 최소 Port는 이 구분을 코드에 드러내며, 복합 조회의 단일 조회 모델
선택권은 유지한다.

## 장점

- 외부 도메인의 저장 구조·상태 정책 변경 영향이 Adapter로 제한된다.
- 예약 준비·확정과 변경 가능 여부 검증의 유스케이스 의도가 의존성에 드러난다.
- 조회 성능을 위해 필요한 복합 조회 구조를 별도 기준으로 유지할 수 있다.

## 단점과 위험

- Port와 Adapter가 늘어 단순한 관계에도 적용하면 오히려 읽기 어려워질 수 있다.
- 활성 상태, 잠금, 예외 변환이 Adapter에 숨겨져도 동작 계약이 바뀌지 않도록 테스트가 필요하다.
- 쓰기·정책 검증과 복합 조회의 경계를 팀이 일관되게 적용해야 한다.

## 검증 방법

- 대상 Application Service와 Validator에 외부 도메인 Repository·Entity·상태 Enum import가 없는지 확인한다.
- Adapter가 기존 TimeSlot 잠금 조회와 Repository 탐색 경로를 사용하고 DTO로 필요한 값만 반환하는지 테스트한다.
- 예약 준비 CREATE·JOIN, 정원 부족, 중복 READY, 예약 확정·모집 마감, 회차·테이블 변경 차단을 회귀 테스트한다.
- `ReservationConfirmationService`의 `Propagation.MANDATORY`와 MySQL 동시성·결제–예약 통합 테스트를 회귀 실행한다.

## 후속 작업

- `TimeSlotService` 조회 기능의 Read Model·Projection 최적화는 V2 조회·성능 개선 Issue로 분리한다.
- `SettlementQueryService`의 복합 조회 Projection 개선은 별도 Issue로 관리한다.
- API, ERD, 예약 상태·정원·예약금·결제 정책은 이 ADR로 변경하지 않는다.
