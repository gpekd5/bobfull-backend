# BobFull Issue 제목 규칙

## 1. 기본 형식

모든 GitHub Issue 제목은 다음 형식을 사용한다.

```text
[v1 | v2 | v3 | project][유형] 작업 내용
```

예시:

```text
[v1][feat] 회원·인증 및 공통 개발 골격 구성
[v2][test] 예약 동시 요청 시 참여 인원 정합성 검증
[v2][fix] 참여자 취소 후 예약 상태 계산 오류 수정
[v3][perf] 예약 가능 좌석 조회 성능 개선
[project][chore] M5 최종 QA·구현 마감 관리
```

## 2. 범위 토큰

첫 번째 토큰은 작업 유형이 아니라 작업 결과가 귀속되는 범위다. `v1`, `v2`, `v3`는 `docs/010-product/project-context.md`에 확정된 범위를 따른다.

| 버전 | 기준 |
|---|---|
| `v1` | 핵심 예약 서비스 가동과 1차 배포 |
| `v2` | 취소·환불·노쇼·채팅 등 정책·운영 안정화 |
| `v3` | 성능·AI·비동기·배포 고도화 |

`project`는 최종 QA·발표·제출·전체 일정·운영처럼 특정 기능 버전에 귀속할 수 없는 프로젝트 공통 작업에만 사용한다. 여러 버전에 영향이 있다는 사실만으로 `project`를 선택하지 않는다.

새 Issue의 범위는 현재 날짜, 현재 개발 단계, 담당자 희망, 템플릿 기본 제목으로 정하지 않는다. 먼저 작업 결과가 어느 확정 기능 범위와 완료 조건을 충족하는지 확인한다. 기존 기능·Issue·마일스톤을 보완하는 `fix`, `test`, `docs`, `refactor`, `perf`는 원칙적으로 대상 기능의 확정 버전을 따른다. 여러 버전에 영향이 있어도 핵심 완료 목적이 하나면 그 버전을 사용한다.

범위가 확정되지 않았거나 문서·기존 Issue가 충돌하면 임의로 `v1`을 붙이지 않고 Human에게 확인한다. 초안 또는 실제 생성 결과에는 버전 판단 근거를 한 줄로 함께 기록한다.

## 3. 유형

Issue 유형은 다음 9개를 사용한다.

| 유형 | 사용 기준 |
|---|---|
| `feat` | 새로운 기능 또는 다른 기능이 의존할 기반 추가 |
| `fix` | 잘못된 동작이나 결함 수정 |
| `test` | 기능 변경 없이 테스트 추가·보강 |
| `docs` | 문서·다이어그램·템플릿만 변경 |
| `refactor` | 동작을 유지하며 내부 구조 개선 |
| `perf` | 성능 개선과 측정 |
| `chore` | 빌드·설정·개발 환경·관리 작업 |
| `spike` | 기술 도입 여부·대안·비용·효과·위험을 조사·검증하고 판단 근거를 남기는 탐색 작업 |
| `infra` | Docker, AWS, 배포 환경, CI/CD, 모니터링 등 인프라 구성과 운영 환경 작업 |

## 4. 유형 선택 기준

- 사용자나 다른 도메인이 사용할 동작·계약이 생기면 `feat`다.
- 코드 결함을 고치면 `fix`다.
- 테스트만 추가하면 `test`다.
- 문서만 바꾸면 `docs`다.
- 외부 동작은 유지하고 내부 구조만 바꾸면 `refactor`다.
- 성능 개선이 목적이고 측정 근거가 있으면 `perf`다.
- 기능이 아닌 설정·환경·단순 관리 작업이면 `chore`다.
- 도입 또는 미도입 판단을 위해 기술 대안과 위험을 조사·검증하면 `spike`다.
- 인프라 구성·배포·운영 환경 자체를 변경하면 `infra`다.

`chore`를 애매한 작업의 기본값으로 사용하지 않는다.
`spike`는 구현 자체보다 판단 근거 확보가 목적일 때만 사용하며, 확정된 인프라 변경을 `spike`로 표기하지 않는다.

## 5. 작성 규칙

- 버전과 유형은 영어 소문자로 작성한다.
- 작업 내용은 한국어로 간결하게 작성한다.
- 제목만 보고 작업 결과를 알 수 있게 작성한다.
- 담당자 이름을 제목에 넣지 않는다.
- 여러 기능을 하나의 제목에 나열하지 않는다.
- 폐기된 정책이나 구현하지 않는 기능명을 사용하지 않는다.

좋은 예:

```text
[v1][feat] 예약 생성 및 최초 참여자 등록 구현
[v2][test] 예약 동시 요청 시 참여 인원 정합성 검증
[v2][docs] 채팅 접근 정책 문서화
[v2][spike] Redis 적용 대상 검토 및 도입 판단
[v1][infra] Docker 실행 환경 구성
[project][chore] M6 발표 준비 일정 관리
[project][docs] 최종 제출 점검 기준 정리
[project][test] 전체 시연 전 최종 점검
```

나쁜 예:

```text
회원 작업
[v1](test) 테스트 추가
[feat] 이것저것 수정
[v1][chore] 예약 기능 구현
[project] M5 최종 QA 관리
[milestone][chore] M5 최종 QA 관리
[project] 프로젝트 공통 작업
```

## 6. Issue·PR·Commit 구분

Issue 제목은 범위와 작업 유형을 함께 표시한다. `[project]`만 단독으로 사용하거나 작업 유형을 생략하지 않는다.

```text
[v1][feat] 회원가입 구현
```

PR과 Commit 제목은 `docs/050-engineering/github-rules.md`의 Conventional Commit 형식을 따른다.

```text
feat: 회원가입 구현
```

Issue와 PR·Commit에서 동일한 유형을 지원하고 작업의 핵심 성격이 같다면 타입을 일치시킨다.
PR·Commit에만 존재하는 타입은 `docs/050-engineering/github-rules.md`를 따르며 Issue 유형에는 사용하지 않는다.

## 7. AI Issue 작성 규칙

AI가 Issue 초안을 만들 때 다음을 확인한다.

1. 실제 GitHub Issue와 확정 문서에서 동일·유사 작업을 먼저 검색한다. 중복이면 새 Issue를 만들지 않고 기존 Issue를 보고한다.
2. `docs/010-product/project-context.md`와 관련 기존 기능·Issue·마일스톤에서 `v1 | v2 | v3 | project` 범위를 판단하고 근거를 기록한다.
3. 실제 작업 성격에 맞는 유형을 선택한다.
4. 제목을 `[범위][유형] 작업 내용`으로 작성한다.
5. 범위나 유형이 불명확하면 추정하지 않고 Human에게 확인한다.
