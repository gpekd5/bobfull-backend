# 결제 트러블슈팅

결제 도메인에서 확인한 문제, 원인, 해결 과정과 검증 상태를 동일한 양식으로 기록한다.

---

# 1. `paymentId` 내부 PK와 외부 식별자 분리

> DB 내부 식별자와 PortOne·외부 API 식별자를 분리해 외부 연동 규칙이 DB 기본키 구조에 결합되는 문제를 해결했다.

---

## 기본 정보

- 날짜: 2026-07-30
- 담당자: 김현승
- 도메인: 결제
- 관련 Issue: #91
- 관련 PR: #98
- 관련 브랜치: `feat/91-payment-ready`
- 상태: `해결됨`

---

## 문제 상황

결제 도메인의 식별자를 설계하면서 DB 내부 기본키와 PortOne 결제 식별자를 하나의 값으로 사용할지 결정해야 했다.

외부 결제 식별자인 `paymentId`를 DB 기본키로 사용하면 구조가 단순해 보이지만, 외부 시스템의 길이·문자 규칙과 API 계약이 내부 DB 관계에 직접 영향을 줄 수 있다.

향후 환불, 결제 이력, 외부 PG 변경 등으로 결제 식별자 정책이 바뀌면 내부 연관관계와 외래키 구조까지 함께 변경해야 하는 문제가 생길 수 있었다.

---

## 원인 분석

### 원인

- 내부 DB 식별자와 외부 결제 식별자의 책임이 구분되지 않았다.
- PortOne에서 사용하는 결제 식별자 규칙이 내부 엔티티 기본키에 직접 결합될 가능성이 있었다.
- 외부 식별자 변경이 내부 외래키와 연관관계에 영향을 줄 수 있었다.

### 원인을 어떻게 확인했는가?

- 로그: 해당 없음
- 디버깅: 해당 없음
- SQL 확인: Payment와 향후 Refund 관계에서 PK·FK 구조가 어떻게 연결되는지 검토했다.
- API 테스트: 외부 API에서는 문자열 `paymentId`를 사용해야 하는 계약을 확인했다.
- AI 분석: 내부 식별자와 외부 공개 식별자를 분리하는 방식의 장단점을 비교했다.
- 기타: Issue #91과 ERD의 Payment 키 구조 충돌을 확인했다.

---

## 해결 과정

### 시도 1

**내용**

PortOne에서 사용하는 `String paymentId`를 Payment 테이블의 기본키로 사용하는 방식을 검토했다.

**결과**

외부 API와 DB에서 같은 식별자를 사용하므로 단순하지만, 외부 결제 규칙이 내부 데이터 모델에 직접 결합되는 문제가 있었다.

향후 외부 결제 서비스 변경이나 식별자 정책 변경 시 내부 연관관계까지 수정해야 할 가능성이 있어 적용하지 않았다.

### 시도 2

**내용**

DB 내부 식별자와 외부 결제 식별자를 분리했다.

- 내부 PK: `Long` 자동 증가 값
- 외부 결제 식별자: UUID 기반 `String paymentId`
- `paymentId`: UNIQUE 제약 적용

**결과**

DB 연관관계는 안정적인 내부 PK를 사용하고, PortOne 요청·조회와 외부 API는 별도의 `paymentId`를 사용할 수 있게 됐다.

### 최종 해결 또는 현재 판단

**적용한 해결 방법 또는 후보안**

- Payment 내부 PK는 `Long`을 사용한다.
- 외부 API와 PortOne 연동에는 UUID 기반 `String paymentId`를 사용한다.
- `paymentId`에는 UNIQUE 제약을 적용한다.

**선택 이유 또는 남은 검증**

내부 저장 구조와 외부 연동 계약을 분리하면 외부 시스템 변경이 DB 기본키와 외래키 구조에 미치는 영향을 줄일 수 있다.

구체적인 접두사, 최대 길이와 허용 문자는 실제 PG 채널 계약에 맞춰 유지해야 한다.

---

## 검증

- 재현 테스트: Issue와 ERD에서 서로 다른 키 구조가 제시된 충돌 상황을 비교했다.
- 자동 테스트: Payment 저장 및 외부 `paymentId` 조회 테스트를 확인했다.
- 직접 검증: Entity의 내부 PK와 외부 `paymentId` 필드 및 UNIQUE 제약을 확인했다.
- 재발 방지: ERD·API 명세·엔티티에서 내부 PK와 외부 식별자의 명칭과 책임을 구분한다.

---

## 배운 점

- DB 기본키와 외부 공개 식별자는 목적이 다르므로 반드시 같은 값을 사용할 필요가 없다.
- 외부 서비스의 규칙을 내부 데이터 모델에 직접 결합하면 변경 범위가 커질 수 있다.
- 식별자 분리는 보안뿐 아니라 연관관계 안정성과 외부 시스템 교체 가능성에도 도움이 된다.

# 2. 좌석 선점 만료와 PG 결제 승인 시점 불일치

> 내부 좌석 선점 만료 이후 외부 결제가 승인될 수 있는 문제를 확인하고, 예약 확정 차단과 운영 보상 로그까지 구현했지만 자동 취소·환불은 남아 있다.

---

## 기본 정보

- 날짜: 2026-07-30
- 담당자: 김현승
- 도메인: 결제 / 예약
- 관련 Issue: #92, #93
- 관련 PR: #101, #107
- 관련 브랜치: `feat/93-portone-webhook-payment-expiration`
- 상태: `검토 중`

---

## 문제 상황

밥풀은 결제를 준비할 때 좌석을 10분간 임시 선점한다.

하지만 PortOne·PG의 결제 승인 시점은 내부 Payment의 `expiresAt`과 독립적으로 동작한다.

예를 들어 사용자가 만료 직전에 결제를 시작하면 다음 상황이 발생할 수 있다.

```text
12:00 READY Payment 생성 및 좌석 임시 점유
12:09 사용자가 결제 시작
12:10 내부 Payment 만료
12:12 PG 결제 승인
```

이 경우 내부 서버는 만료된 Payment이므로 예약을 확정할 수 없지만, 외부에서는 이미 결제가 승인된 상태가 된다.

즉, 결제는 완료됐지만 예약은 실패하는 결과가 발생할 수 있다.

---

## 원인 분석

### 원인

- 내부 좌석 선점 만료와 외부 PG 승인 시점이 서로 독립적이다.
- 프론트 타이머는 새로운 결제 시작은 막을 수 있지만 이미 열린 결제창과 외부 인증 과정을 완전히 중단할 수 없다.
- 자동 승인 방식에서는 PG 승인 직전에 서버가 좌석과 만료 상태를 다시 확인하기 어렵다.

### 원인을 어떻게 확인했는가?

- 로그: 외부 PAID·내부 만료 상황에서 `PAYMENT_COMPENSATION_REQUIRED` 로그를 남기도록 구현했다.
- 디버깅: 완료 API와 웹훅이 외부 결제를 재조회한 뒤 내부 만료 상태를 확인하는 흐름을 검토했다.
- SQL 확인: 해당 없음
- API 테스트: 만료된 Payment 완료 요청이 `409 PAYMENT_EXPIRED`로 거절되는지 확인했다.
- AI 분석: 프론트 차단, 승인 후 취소, PortOne V2 수동 승인 방식을 비교했다.
- 기타: 실제 PG 승인 시점과 내부 `expiresAt`이 독립적이라는 계약을 확인했다.

---

## 해결 과정

### 시도 1

**내용**

프론트엔드에서 10분 타이머가 끝나면 결제 버튼을 비활성화하고 새로운 결제창 호출을 차단하는 방식을 검토했다.

**결과**

새로운 결제 시작은 줄일 수 있지만 이미 열린 결제창과 진행 중인 외부 인증은 완전히 중단할 수 없었다.

근본 해결이 아니라 보조 수단으로 판단했다.

### 시도 2

**내용**

내부 만료 이후 외부 결제가 승인되면 예약 확정은 거절하고 즉시 결제를 취소하는 방식을 검토했다.

**결과**

결제와 예약의 불일치는 보상할 수 있지만, 카드 취소 반영까지 시간이 걸릴 수 있고 자동 취소·환불 트랜잭션이 추가로 필요했다.

현재 PR #107 범위에서는 자동 보상을 구현하지 않고 구조화 로그만 남겼다.

### 최종 해결 또는 현재 판단

**적용한 해결 방법 또는 후보안**

- 완료 API는 EXPIRED 또는 만료된 READY를 `409 PAYMENT_EXPIRED`로 거절한다.
- 웹훅에서 외부 결제가 PAID이지만 내부 Payment가 EXPIRED 또는 만료 READY이면 상태 전이와 예약 확정을 하지 않는다.
- 운영자가 확인할 수 있도록 `PAYMENT_COMPENSATION_REQUIRED` 구조화 로그를 남긴다.
- 장기적으로는 PortOne V2 수동 승인 또는 자동 취소·환불 보상 흐름을 검토한다.

**선택 이유 또는 남은 검증**

현재 구현은 만료된 좌석에 예약이 확정되는 문제는 막는다.

다만 이미 승인된 외부 결제의 자동 취소·환불은 구현하지 않았으므로 완전한 해결은 아니다.

실제 PG 채널의 수동 승인 지원 여부와 테스트 채널 동작을 확인해야 한다.

---

## 검증

- 재현 테스트: 내부 만료 후 외부 PAID 응답이 들어오는 상황을 테스트로 구성했다.
- 자동 테스트: 만료 완료 거절, 웹훅 보상 로그, 상태 전이 및 예약 확정 미실행을 확인했다.
- 직접 검증: PR #107의 완료 처리·웹훅·보상 로그 흐름을 검토했다.
- 재발 방지: 만료 상태를 락 획득 후 다시 검증하고 외부 PAID·내부 만료 상황을 구조화 로그로 관찰한다.

---

## 배운 점

- 내부 만료 시각과 외부 결제 승인 시각은 하나의 트랜잭션으로 묶을 수 없다.
- 프론트 타이머만으로 외부 결제 과정을 완전히 통제할 수 없다.
- 결제 승인과 예약 결과가 갈라지는 경우를 대비해 보상 정책과 운영 관찰 수단이 필요하다.
- 예약 확정을 막는 것과 이미 승인된 결제를 복구하는 것은 별도의 문제다.

# 3. PortOne SDK 동기 대기와 외부 API 예외 변환 미검증

> PortOne SDK의 동기 대기와 외부 오류 변환 정책이 실제 연동 환경에서 충분히 검증되지 않아 장애 상황의 응답 정책이 불명확하다.

---

## 기본 정보

- 날짜: 2026-07-30
- 담당자: 김현승
- 도메인: 결제 / 외부 연동
- 관련 Issue: #92
- 관련 PR: #101
- 관련 브랜치: 확인 필요
- 상태: `검토 중`

---

## 문제 상황

`PortOneSdkPaymentReader.read(...)`는 PortOne SDK의 비동기 결제 조회 결과에 `join()`을 호출해 동기적으로 응답을 기다린다.

정상 응답에서는 문제가 없지만 PortOne 응답 지연, 네트워크 장애, 인증 오류, 존재하지 않는 결제 조회와 같은 상황에서 어떤 예외가 발생하고 클라이언트에 어떤 응답을 반환할지 충분히 검증되지 않았다.

외부 SDK 예외가 내부 결제 예외로 변환되지 않으면 모든 문제가 일반 `INTERNAL_SERVER_ERROR`로 처리될 수 있다.

---

## 원인 분석

### 원인

- 외부 결제 조회를 동기적으로 기다리지만 애플리케이션 차원의 명시적인 대기 시간 정책이 없다.
- PortOne SDK 예외를 내부 `PaymentErrorCode`로 변환하는 Adapter 경계가 구현되지 않았다.
- 실제 테스트 채널에서 오류 유형별 SDK 예외 구조를 확인하지 않았다.
- 재시도 가능한 오류와 재시도하면 안 되는 오류의 기준이 정해지지 않았다.

### 원인을 어떻게 확인했는가?

- 로그: 실제 외부 API 장애 로그는 아직 확보하지 못했다.
- 디버깅: `join()`을 통해 외부 응답을 동기 대기하는 코드를 확인했다.
- SQL 확인: 해당 없음
- API 테스트: 정상 결제 조회 중심으로 검증했으며 장애 상황은 미검증이다.
- AI 분석: 타임아웃, 재시도와 예외 변환은 서로 다른 정책이라는 점을 비교했다.
- 기타: 사용 중인 PortOne SDK의 기본 HTTP 타임아웃 설정을 확인했다.

---

## 해결 과정

### 시도 1

**내용**

PortOne SDK의 기본 HTTP 타임아웃에 의존하고, 외부 예외는 전역 예외 처리기로 전달하는 현재 구조를 유지했다.

**결과**

정상 흐름은 동작하지만 결제 미존재, 인증 오류, 네트워크 장애와 외부 서버 오류를 내부에서 구분하기 어렵다.

로그와 클라이언트 응답 정책도 세밀하게 나눌 수 없다.

### 시도 2

**내용**

외부 SDK Adapter에서 예외를 분류하고 내부 `PaymentErrorCode` 기반 예외로 변환하는 방향을 검토했다.

**결과**

방향은 적절하지만 실제 SDK가 반환하는 예외 타입과 원인을 테스트 채널에서 확인하지 못해 아직 적용하지 않았다.

### 최종 해결 또는 현재 판단

**적용한 해결 방법 또는 후보안**

- 외부 결제 조회 최대 대기 시간 정책을 정의한다.
- 연결 실패, 응답 지연, 인증 오류, 결제 미존재와 외부 서버 오류를 구분한다.
- PortOne SDK 예외를 Adapter에서 내부 `PaymentErrorCode`로 변환한다.
- 내부 로그에는 원인을 보존하고 클라이언트에는 안전한 메시지만 반환한다.
- 재시도는 대상 예외, 횟수와 간격을 별도로 결정한다.

**선택 이유 또는 남은 검증**

SDK의 실제 오류 응답을 확인하지 않은 상태에서 예외 타입을 추측해 구현하면 잘못된 분류가 생길 수 있다.

테스트 채널에서 오류 상황을 재현한 뒤 정책을 확정해야 한다.

---

## 검증

- 재현 테스트: 정상 조회 외 장애 상황은 아직 재현하지 못했다.
- 자동 테스트: SDK Adapter 정상 변환 테스트만 존재하며 외부 장애 예외 매핑은 추가가 필요하다.
- 직접 검증: SDK 내부 기본 타임아웃과 현재 `join()` 호출 구조를 확인했다.
- 재발 방지: 실제 오류 유형별 테스트를 작성하고 외부 SDK 예외가 서비스 계층으로 직접 누출되지 않도록 Adapter 경계를 둔다.

---

## 배운 점

- 비동기 API에 `join()`을 사용한다고 타임아웃이나 재시도가 자동으로 해결되는 것은 아니다.
- 외부 SDK 예외를 서비스 내부 예외로 변환하는 경계가 필요하다.
- 타임아웃, 재시도와 예외 변환은 각각 별도의 정책으로 설계해야 한다.
- 실제 외부 연동 오류를 확인하지 않고 예외 타입을 추측해서는 안 된다.

---

# 4. 락 획득 후 Payment 만료 재검증

> 외부 조회와 DB 락 대기 사이에 Payment가 만료될 수 있어, 실제 상태 변경 직전에 만료를 다시 확인하도록 개선했다.

---

## 기본 정보

- 날짜: 2026-07-30
- 담당자: 김현승
- 도메인: 결제 / 동시성
- 관련 Issue: #92, #93
- 관련 PR: #101, #107
- 관련 브랜치: `feat/93-portone-webhook-payment-expiration`
- 상태: `해결됨`

---

## 문제 상황

결제 완료 흐름은 다음 두 단계로 나뉜다.

```text
PaymentCompletionService
→ 기본 검증과 PortOne 결제 재조회

PaymentCompletionTransactionService
→ Payment 행 락 획득과 PAID 상태 전이
```

최초 만료 검사와 실제 PAID 전환 사이에는 PortOne 응답 대기와 DB 락 대기 시간이 있다.

최초 검사 당시에는 유효했던 Payment가 락을 획득할 때는 만료될 수 있었다.

이 상태에서 최초 검증 결과만 믿고 PAID로 변경하면 이미 만료된 결제가 예약으로 확정되는 TOCTOU 경쟁 조건이 발생한다.

---

## 원인 분석

### 원인

- 검증 시점과 실제 상태 변경 시점이 분리돼 있었다.
- 외부 API 응답과 DB 락을 기다리는 동안 시간이 흐를 수 있었다.
- 락은 동시 수정을 막지만 락 대기 중 발생한 시간 조건 변화까지 자동으로 검증하지 않는다.

### 원인을 어떻게 확인했는가?

- 로그: 해당 없음
- 디버깅: 완료 서비스와 트랜잭션 서비스 사이의 호출 순서를 추적했다.
- SQL 확인: `findWithLockById`를 통한 Payment 행 비관적 락 사용을 확인했다.
- API 테스트: 만료된 Payment 완료 요청이 거절되는지 확인했다.
- AI 분석: 검사 시점과 사용 시점이 달라지는 TOCTOU 경쟁 조건으로 분석했다.
- 기타: 고정 `Clock`을 사용해 락 대기 중 만료되는 경계를 테스트했다.

---

## 해결 과정

### 시도 1

**내용**

`PaymentCompletionService`에서 PortOne 재조회 전에 한 번만 만료 여부를 확인했다.

**결과**

외부 API 호출과 락 대기 중 Payment가 만료되는 경우를 막지 못했다.

최초 검사 결과가 실제 상태 변경 시점까지 유효하다는 보장이 없었다.

### 시도 2

**내용**

`PaymentCompletionTransactionService.complete()`에서 Payment 행 락을 획득한 직후 현재 시각을 다시 가져와 `expiresAt`을 재검증했다.

같은 기준 시각을 만료 판단과 `paidAt` 기록에 함께 사용했다.

**결과**

락 대기 중 만료된 Payment는 PAID로 전환되지 않았고 예약 확정 Port도 호출되지 않았다.

### 최종 해결 또는 현재 판단

**적용한 해결 방법 또는 후보안**

- Payment 행에 비관적 락을 획득한다.
- 락 획득 직후 `Clock`으로 기준 시각을 한 번 생성한다.
- 그 시각으로 상태와 만료 여부를 다시 확인한다.
- 유효한 READY만 PAID로 전환하고 예약 확정을 호출한다.
- 만료된 Payment는 `PAYMENT_EXPIRED`로 거절한다.

**선택 이유 또는 남은 검증**

락 획득 후 재검증해야 실제 상태 변경 시점의 최신 상태를 기준으로 판단할 수 있다.

동일한 시각을 만료 판단과 `paidAt`에 사용하면 한 요청 안에서 시간 기준이 달라지는 문제도 방지할 수 있다.

---

## 검증

- 재현 테스트: 고정 `Clock`으로 최초 검사 후 락 대기 중 만료되는 상황을 재현했다.
- 자동 테스트: READY 유지, Payment 완료 미호출과 ReservationConfirmationPort 미호출을 검증했다.
- 직접 검증: 완료 서비스와 트랜잭션 서비스의 락·재검증 순서를 확인했다.
- 재발 방지: 외부 호출이나 락 대기 후 상태 변경 직전에 상태와 시간 조건을 다시 검증한다.

---

## 배운 점

- 락을 사용해도 락 획득 전 검증 결과가 최신 상태라는 보장은 없다.
- 외부 API 호출과 락 대기가 있는 흐름에서는 상태 변경 직전 재검증이 필요하다.
- 시간 조건 테스트에는 시스템 시간을 직접 호출하지 않고 `Clock`을 주입하는 것이 유리하다.
- 하나의 처리 안에서 만료 판단과 상태 기록은 같은 기준 시각을 사용해야 한다.

# 5. 웹훅 서명 경계와 외부 PAID·내부 EXPIRED 관찰

> 인증 없이 접근 가능한 웹훅에서 서명 검증 전 처리를 막고, 외부 승인과 내부 만료가 갈라지는 상황을 운영 보상 대상으로 기록하도록 구현했다.

---

## 기본 정보

- 날짜: 2026-07-30
- 담당자: 김현승
- 도메인: 결제 / 보안 / 외부 연동
- 관련 Issue: #93
- 관련 PR: #107
- 관련 브랜치: `feat/93-portone-webhook-payment-expiration`
- 상태: `검토 중`

---

## 문제 상황

PortOne 웹훅은 사용자 JWT 없이 외부 서버에서 애플리케이션으로 전달된다.

따라서 Security 설정에서는 웹훅 경로를 열어야 하지만, `permitAll`이라는 이유만으로 요청을 신뢰하면 공격자가 위조한 결제 완료 요청을 보낼 수 있다.

또한 정상 서명의 웹훅이더라도 외부에서는 PAID인데 내부 Payment가 이미 만료된 경우 결제와 예약 결과가 달라질 수 있다.

---

## 원인 분석

### 원인

- 웹훅은 일반 사용자 인증 방식인 JWT를 사용할 수 없다.
- `permitAll`은 요청 진입을 허용할 뿐 요청의 진위를 보장하지 않는다.
- JSON을 먼저 변환하거나 결제 처리를 시작한 뒤 서명을 검증하면 위조 요청이 내부 로직에 도달할 수 있다.
- 외부 결제 상태와 내부 Payment 만료 상태가 독립적으로 변경될 수 있다.

### 원인을 어떻게 확인했는가?

- 로그: 외부 PAID·내부 만료 상황에서 `PAYMENT_COMPENSATION_REQUIRED` 구조화 로그를 확인했다.
- 디버깅: Controller가 원본 Body와 서명 헤더를 Verifier에 전달한 뒤에만 paymentId를 처리하는 순서를 확인했다.
- SQL 확인: 해당 없음
- API 테스트: 헤더 누락과 서명 실패 시 400, JWT 없는 정상 진입, 영구 업무 실패 시 200 정책을 검증했다.
- AI 분석: Security 진입 허용과 웹훅 신뢰 검증은 서로 다른 책임으로 분석했다.
- 기타: 실제 PortOne 테스트 채널 전달은 외부 공개 URL이 준비되지 않아 실행하지 못했다. (2026-07-30 smee.io 터널로 실제 채널 검증 완료, 아래 "후속 검증" 참고)

---

## 해결 과정

### 시도 1

**내용**

웹훅 경로를 `permitAll`로 설정하고 일반 Controller 요청처럼 JSON을 바로 처리하는 방식을 검토했다.

**결과**

외부 요청이 애플리케이션에 도달할 수는 있지만 위조 요청을 구분할 수 없었다.

`permitAll`을 신뢰 검증으로 오해하면 결제 상태가 임의로 변경될 위험이 있어 적용하지 않았다.

### 시도 2

**내용**

Controller에서 원본 Body와 `webhook-id`, `webhook-signature`, `webhook-timestamp`를 공식 SDK Adapter에 전달해 서명을 먼저 검증했다.

검증 성공 후에만 이벤트 종류와 paymentId를 해석하고 공통 결제 완료 처리로 전달했다.

**결과**

헤더 누락과 서명 실패 요청이 Payment 조회·상태 전이·예약 확정 로직에 진입하지 않도록 차단했다.

외부 PAID·내부 만료 상황은 예약 확정 없이 보상 필요 로그로 남겼다.

### 최종 해결 또는 현재 판단

**적용한 해결 방법 또는 후보안**

- 웹훅 경로는 `permitAll`로 열고 JWT 필터에서는 제외한다.
- 원본 Body와 PortOne 서명 헤더를 먼저 검증한다.
- 검증 성공 후에만 JSON 이벤트와 paymentId를 사용한다.
- 외부 PAID·내부 EXPIRED 또는 만료 READY이면 상태 전이와 예약 확정을 수행하지 않는다.
- 구조화된 `PAYMENT_COMPENSATION_REQUIRED` 로그를 남긴다.

**선택 이유 또는 남은 검증**

로컬 WebMvc·Security·SDK Adapter 테스트로 애플리케이션 경계는 검증했다.

자동 취소·환불도 후속 범위다.

---

## 검증

- 재현 테스트: 헤더 누락, 잘못된 서명과 외부 PAID·내부 만료 상황을 테스트로 구성했다.
- 자동 테스트: WebMvc, Security, SDK Adapter와 보상 로그 테스트를 통과했다.
- 직접 검증: 원본 Body가 변형되지 않고 Verifier로 전달되는 호출 순서를 확인했다.
- 재발 방지: 웹훅 Controller에서 서명 검증 전 JSON 해석과 업무 처리를 금지하고 실제 채널 테스트를 후속 검증 항목으로 유지한다.

---

## 배운 점

- `permitAll`은 인증 생략이 아니라 외부 요청이 들어올 수 있게 하는 진입 설정이다.
- 웹훅의 신뢰 여부는 JWT가 아니라 제공자의 서명 검증으로 판단해야 한다.
- 서명 검증에는 파싱 후 객체가 아니라 원본 Body가 필요하다.
- 외부 결제 성공과 내부 예약 성공은 항상 같은 결과가 아니므로 운영 보상 경로가 필요하다.
- 자동 보상을 구현하지 않았다면 해결 완료로 과장하지 않고 미검증·후속 범위를 남겨야 한다.

---

## 후속 검증 (2026-07-30 실채널 테스트)

Postman 예약 준비 API로 실제 `paymentId`/`amount`를 발급받고, 프론트 개발자 테스트 페이지(`/dev/payment-test`)에서 실제 KG이니시스 테스트 결제를 진행한 뒤 smee.io 공개 터널로 로컬 백엔드까지 웹훅을 릴레이해 아래를 확인했다.

- **정상 결제 흐름**: `Transaction.Ready` → `Transaction.Paid` 웹훅이 정상 수신되고, 서명 검증을 통과해 Payment READY → PAID 전환과 `reservation`/`reservation_participant` 생성까지 한 트랜잭션에서 정상 처리되는 것을 로그와 DB로 확인했다.
- **서명 헤더 누락 / 잘못된 서명**: 둘 다 `400`으로 거부되었고, Payment 조회·락 획득·예약 생성 등 후속 SQL이 전혀 실행되지 않아 서명 검증 단계에서 확실히 차단됨을 확인했다.
- **동일 이벤트 재전송(멱등성)**: 최초 처리 후 같은 `Transaction.Paid` 이벤트를 재전송하면 `portone_payment_id`로 Payment를 조회만 하고, `for update` 락 획득이나 `reservation`/`reservation_participant` insert, `payment` update가 재실행되지 않는 것을 확인했다. 즉 중복 웹훅에 대해 예약이 중복 생성되거나 결제가 재처리되지 않는다. (최종 HTTP 응답 코드까지 포함한 자동 테스트화는 후속 필요)
- **운영 관찰**: 로컬 백엔드가 재시작 등으로 잠시 내려가 있는 동안 smee-client로 도착한 웹훅은 `ECONNREFUSED`로 유실되며 자동 재시도되지 않았다. 실제 채널 테스트 시 백엔드를 먼저 기동한 뒤 웹훅 릴레이를 시작해야 하고, 유실된 이벤트는 smee 대시보드에서 수동 재전송해야 한다.

자동 취소·환불 보상 흐름은 여전히 미구현이므로 `상태: 검토 중`은 유지한다.

- 상태: `해결됨`

## 문제 상황

사용자가 결제를 시작하면 결제 완료 전이라도 해당 좌석을 다른 사용자가 예약하지 못하도록 일정 시간 임시 점유해야 한다.

하지만 READY 결제가 만료됐는데도 계속 사용 중인 좌석으로 계산하면 검색 화면의 잔여석과 실제 예약 가능 좌석이 달라진다.

예를 들어 전체 정원이 4명이고 결제 완료 좌석이 2명, 만료된 READY가 1명이라면 실제로는 2명이 더 예약할 수 있어야 한다.

만료된 READY까지 점유 좌석으로 계산하면 검색 화면에는 남은 좌석이 1명으로 표시된다.

반대로 아직 유효한 READY를 잔여석으로 표시하면 두 사용자가 같은 좌석을 동시에 결제할 수 있다.

---

## 원인 분석

### 원인

- READY 상태만 확인하고 만료 시각을 확인하지 않으면 만료된 좌석이 계속 점유된 것으로 처리된다.
- Scheduler가 EXPIRED로 상태를 변경한 뒤에만 좌석을 반환하면 Scheduler 지연이나 실패 시 좌석이 불필요하게 잠긴다.
- 검색 도메인과 결제 도메인이 서로 다른 만료 기준을 사용하면 잔여석과 실제 예약 가능 여부가 달라질 수 있다.

### 원인을 어떻게 확인했는가?

- 로그: 외부 PAID·내부 만료 상황은 `PAYMENT_COMPENSATION_REQUIRED` 로그로 구분했다.
- 디버깅: 결제 완료와 만료 Processor가 락 획득 후 상태와 만료 시각을 다시 확인하는 흐름을 검토했다.
- SQL 확인: 검색 QueryDSL 서브쿼리가 `READY && expiresAt > now` 조건만 합산하는 것을 확인했다.
- API 테스트: 모집 중 예약 검색에서 유효한 READY만 잔여석 계산에 반영되는지 확인했다.
- AI 분석: 이커머스 재고 선차감·복구 방식과 원본 데이터 계산 방식을 비교했다.
- 기타: PR #106의 검색 계산과 PR #107의 결제 만료 기준을 함께 비교했다.

## 해결 과정

### 시도 1

**내용**

READY 결제가 생성될 때 별도의 잔여 좌석 숫자를 감소시키고, 만료 시 다시 증가시키는 방식을 검토했다.

```text
잔여 좌석 4
→ READY 생성
→ 잔여 좌석 3

READY 만료
→ 잔여 좌석 4로 복구
```

**결과**

복구 작업이 실패하면 빈 좌석이 계속 잠길 수 있고, 중복 실행되면 실제 정원보다 잔여 좌석이 많아질 수 있었다.

복구 로직 자체가 새로운 정합성 위험을 만들 수 있어 적용하지 않았다.

### 시도 2

**내용**

좌석 숫자를 직접 변경하지 않고 결제와 참여 원본 데이터를 조회해 사용 중인 좌석을 계산했다.

```text
사용 중 좌석
= 결제 완료 좌석
+ READY이면서 expiresAt > 현재 시각인 좌석
```

**결과**

READY 상태가 아직 EXPIRED로 변경되지 않았더라도 만료 시각이 지나면 검색 계산에서 자동으로 제외됐다.

Scheduler가 늦게 실행돼도 검색 결과에서 좌석이 계속 잠기지 않았다.

### 최종 해결 또는 현재 판단

**적용한 해결 방법 또는 후보안**

- 결제 도메인에서 READY Payment의 `expiresAt`을 관리한다.
- 완료 처리와 만료 처리에서 Payment 행 락 획득 후 상태와 만료 시각을 재검증한다.
- 만료된 READY는 EXPIRED로 상태를 정규화한다.
- 검색 잔여석은 `status = READY AND expiresAt > 현재 시각`인 결제만 임시 점유로 계산한다.
- Scheduler는 좌석 숫자 복구가 아니라 Payment 상태 정규화를 담당한다.

**선택 이유 또는 남은 검증**

원본 데이터를 기준으로 계산하면 복구 실패나 중복 복구로 인한 잔여석 불일치 위험을 줄일 수 있다.

검색 쿼리가 만료 시각을 직접 확인하므로 Scheduler 실행 여부와 관계없이 좌석을 다시 노출할 수 있다.

다만 좌석 계산 조건이 검색 Repository, `AvailableCapacityCalculator`, `PaymentHoldReader` 등에 나뉘어 있으므로 향후 공통 정책 또는 공통 Reader로 통합할 필요가 있다.

## 검증

- 재현 테스트: 정원 4명, 결제 완료 2명, 만료 전 READY 1명과 만료 후 READY 1명 조건을 비교했다.
- 자동 테스트: 결제 만료 전이, 완료 시 만료 재검증, 검색 Repository 유효 READY 합산과 완료·만료 동시성 테스트를 확인했다.
- 직접 검증: QueryDSL의 `READY && expiresAt > now` 조건과 PR #107의 만료 기준을 비교했다.
- 재발 방지: `Clock`으로 시각을 고정하고 검색·예약 가능 인원·완료 처리에서 동일한 만료 계약을 사용한다.

## 배운 점

- 좌석이나 재고를 반드시 직접 차감하고 복구해야 하는 것은 아니다.
- 원본 상태와 만료 시각을 기준으로 계산하면 별도 복구 없이 좌석을 다시 노출할 수 있다.
- Scheduler는 좌석 복구의 유일한 수단이 아니라 DB 상태를 정리하는 보조 장치로 사용할 수 있다.
- 검색 잔여석과 실제 예약 가능 여부는 같은 결제 상태와 만료 기준을 사용해야 한다.
- 서로 다른 도메인에서 같은 공식을 중복 구현하면 정책 변경 시 정합성이 깨질 수 있다.

# 7. 프론트-백엔드 간 CORS 미허용 및 preflight 인증 차단

> 프론트(localhost:5173)에서 결제 완료 API를 직접 호출하면 CORS 설정 부재와 Security의 OPTIONS 인증 요구로 브라우저 요청이 아예 차단되던 문제를 CORS 설정 추가와 preflight 인증 예외 처리로 해결했다.

---

## 기본 정보

- 날짜: 2026-07-30
- 담당자: 김현승
- 도메인: 결제 / 인프라
- 관련 Issue: #93
- 관련 PR: #107
- 관련 브랜치: `feat/93-portone-webhook-payment-expiration`
- 상태: `해결됨`

---

## 문제 상황

프론트(`bobfull-frontend`, `http://localhost:5173`)에서 개발자 테스트 페이지를 통해 `POST /api/payments/{paymentId}/complete`를 직접 호출하면 브라우저에서 `Network Error`가 발생했다.

Postman으로 같은 API를 호출하면 정상적으로 401(미인증) 또는 200 응답을 받아, 백엔드 자체는 정상 동작하는 것으로 보였다.

---

## 원인 분석

### 원인

- 백엔드에 `http://localhost:5173` origin을 허용하는 CORS 설정이 없었다.
- Spring Security가 `OPTIONS` preflight 요청까지 인증을 요구하고 있어, CORS 허용 여부와 무관하게 사전 확인 단계에서부터 401로 차단됐다.

### 원인을 어떻게 확인했는가?

- 로그: 브라우저 axios가 `Network Error`만 반환해 원인 파악에 직접 도움이 되지 않았다.
- 디버깅: `curl -X OPTIONS`로 동일한 preflight 요청을 직접 재현했다.
- SQL 확인: 해당 없음
- API 테스트: `curl` OPTIONS 요청에 `Access-Control-Allow-Origin` 헤더가 없고 `401 UNAUTHORIZED` 응답이 오는 것을 확인했다. 같은 origin으로 실제 POST를 보내면 백엔드까지는 도달하되 CORS 헤더 부재로 브라우저가 응답을 차단한다는 것을 추론했다.
- AI 분석: Postman은 브라우저가 아니므로 CORS 제약을 받지 않는다는 점, Spring Security 활성화 시 `WebMvcConfigurer`만으로는 CORS가 적용되지 않고 `SecurityFilterChain`에 `CorsConfigurationSource`를 명시적으로 연결해야 한다는 점을 확인했다.
- 기타: 해당 없음

---

## 해결 과정

### 시도 1

**내용**

`WebMvcConfigurer.addCorsMappings`만으로 CORS를 허용하는 방식을 검토했다.

**결과**

Spring Security가 활성화된 상태에서는 Security 필터 체인이 먼저 요청을 가로채 인증을 요구하므로, MVC 레벨의 CORS 설정만으로는 preflight 차단 문제가 해결되지 않는다.

### 시도 2

**내용**

`CorsConfigurationSource` 빈을 정의하고 `SecurityFilterChain`에 `.cors(cors -> cors.configurationSource(...))`로 연결했다. 동시에 `authorizeHttpRequests`에 `.requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()`을 추가해 preflight만 인증 예외로 뒀다.

**결과**

`curl` preflight 재현 시 `200`과 `Access-Control-Allow-Origin: http://localhost:5173` 헤더가 정상 반환됐고, 인증 없는 실제 POST 요청은 여전히 `401`로 유지되어 엔드포인트 자체의 인증 요구사항은 약화되지 않았음을 확인했다.

### 최종 해결 또는 현재 판단

**적용한 해결 방법 또는 후보안**

- `CorsConfigurationSource` 빈을 추가하고 허용 origin은 `cors.allowed-origins` 환경변수(`CORS_ALLOWED_ORIGINS`)로 분리해 로컬/운영을 구분한다.
- `SecurityFilterChain`에 CORS 설정을 명시적으로 연결한다.
- `OPTIONS` 요청만 인증 예외 처리하고, 그 외 실제 요청(`GET/POST/PUT/DELETE`)의 인증 요구사항은 그대로 유지한다.

**선택 이유 또는 남은 검증**

Security와 CORS를 함께 쓸 때는 MVC 레벨 설정과 Security 필터 체인 레벨 설정이 분리되어 있다는 점을 놓치기 쉬워, 이후 유사한 프론트-백엔드 연동 문제에서 재확인이 필요하다.

운영 origin 값은 실제 배포 도메인으로 `CORS_ALLOWED_ORIGINS`를 설정해야 하며, 와일드카드(`*`)는 credentials 허용과 함께 쓰지 않는다.

## 검증

- 재현 테스트: `curl -X OPTIONS`로 실제 브라우저 preflight 요청을 재현해 수정 전/후 응답을 비교했다.
- 자동 테스트: `SecurityConfigWebTest`에 preflight 200·CORS 헤더 검증, 인증 없는 POST 401 유지 검증 테스트 2건을 추가했다.
- 직접 검증: 프론트 개발자 테스트 페이지(`/dev/payment-test`)에서 로그인 상태로 실제 완료 API를 호출해 `paymentStatus: PAID` 응답까지 수신되는 것을 확인했다.
- 재발 방지: Security 활성화 프로젝트에서 CORS를 추가할 때는 `WebMvcConfigurer`가 아니라 `SecurityFilterChain`에 `CorsConfigurationSource`를 연결해야 한다는 점, `OPTIONS`는 별도로 인증 예외 처리해야 한다는 점을 팀 공유 사항으로 남긴다.

---

## 배운 점

- CORS는 브라우저가 강제하는 규칙이라 Postman·curl 같은 비브라우저 클라이언트로는 재현되지 않는다. "Postman은 되는데 프론트는 안 된다"는 현상 자체가 CORS를 의심할 신호다.
- Spring Security가 활성화된 프로젝트에서는 CORS 설정이 MVC 레벨이 아니라 Security 필터 체인 레벨에 연결되어야 실제로 동작한다.
- `OPTIONS` preflight는 실제 데이터를 읽거나 바꾸지 않으므로 인증 예외 처리해도 보안이 약화되지 않는다. 반면 실제 요청 메서드의 인증은 그대로 유지해야 한다.
- 브라우저 쪽 에러 메시지(`Network Error`)만으로는 원인을 알 수 없고, `curl`로 동일 요청을 직접 재현하는 것이 원인 파악에 가장 빨랐다.
