# BobFull V1 Flow Lab

## 목적

**사장님 또는 일반 사용자가 BobFull V1 기능을 직접 실행하면서, 그 행동 뒤에서 어떤
API·Controller·Service·Port·Repository·트랜잭션·락·DB 상태 변화가 발생하는지 확인하는
사용자 여정 기반 백엔드 시뮬레이터**입니다.

기술 레이어와 세부 코드 단계를 먼저 늘어놓지 않고, "사장님/사용자가 무엇을 하는가" →
"API 요청" → "BobFull Backend 내부 처리" → "PortOne·MySQL 호출" → "상태·트랜잭션·락
변화" → "최종 응답" 순서로 큰 흐름을 먼저 보여준 뒤, 필요할 때만 실제 코드·증거·설계
설명을 펼쳐 볼 수 있게 구성했습니다.

화면은 상단의 **Chapter Navigation·시나리오 설정·실행**, 중앙 전체 폭의 **주체 기반
Flowchart/Swimlane**, 그 아래의 **현재 실행 코드·핵심 상태**, 하단의 **Timeline·실행 제어**와
상세 탭으로 구성됩니다. Flowchart는 사용자 → BobFull Backend → PortOne → MySQL 레인에서
큰 흐름 그룹을 먼저 보여주고, 현재 그룹과 이동 방향을 강조합니다. 각 그룹 아래에는 기존
세부 단계가 그대로 남아 있으며, 단계·그룹·Timeline을 클릭해 바로 이동할 수 있습니다.

## 이것은 실제 실행기가 아닙니다

이 화면은 실제 JVM·Spring Boot·MySQL·PortOne을 실행하지 않습니다. 아래 기준 Commit의
**실제 코드와 테스트를 사람이 읽고 정리한 재생 데이터**를 `app.js`에 담아, "이 코드가 이
순서로 실행되면 상태·트랜잭션·락·응답이 어떻게 바뀌는가"를 재생하는 시뮬레이터입니다.

- 실제 PortOne API를 호출하지 않습니다.
- 실제 DB에 연결하지 않습니다.
- 운영 데이터를 사용하지 않습니다.
- 역할 조작 영역(사장님/사용자 입력값)은 Flow Lab 내부 가상 테스트 데이터이며, 실제
  로그인·결제·서버 요청을 전송하지 않습니다.

## 정보 구조 (3단계 계층)

1. **V1 전체 사용자 여정** — 상단 Chapter Navigation(Ch1~Ch5). 각 Chapter는 기술 이름이
   아니라 실제 사용자 목적(사장님 준비, 사용자 탐색, 예약·결제 준비, 결제 완료·예약 확정,
   예약·정산 확인)을 나타냅니다.
2. **선택한 행동의 핵심 백엔드 흐름** — Chapter 안에서 "사용자 행동"(예: 로그인, 식당
   등록, 결제 완료)을 고르면 한 줄 설정 바와 6~9개 정도의 큰 단계("핵심 백엔드 흐름")가
   먼저 보입니다. 세부 코드 단계는 삭제하지 않고 큰 흐름 바로 아래의 단계 목록으로 유지합니다.
3. **실제 코드와 기술 근거** — 큰 단계를 클릭해 펼치면 그 안의 세부 단계가 나오고, 세부
   단계를 하나 선택했을 때만 실제 코드·API 근거·트랜잭션/락 상태·성능 관찰·테스트 근거·
   설계 이유가 하단 탭(실제 코드/실행 증거/설계 설명/성능 관찰)에 표시됩니다. 실행 전에는
   결과·코드·증거가 미리 노출되지 않습니다.

## Chapter 구성과 실제 코드 연결 상태

| Chapter | 역할 | 상태 | 설명 |
|---|---|---|---|
| Ch1. 사장님 준비 | 사장님 | 연결됨 | 로그인 / 식당 등록 / 테이블 등록 / 회차 등록 |
| Ch2. 사용자 탐색 | 일반 사용자 | 연결됨 | 로그인 / 식당 검색 / 식당 상세 조회 / 예약 가능 회차 조회 |
| Ch3. 예약·결제 준비 | 일반 사용자 | 연결됨 | CREATE/JOIN 토글로 예약금 계산과 READY Payment 발급 |
| Ch4. 결제 완료·예약 확정 | 일반 사용자 | 연결됨 | 정상 완료 / 중복 요청(락 이전·이후) / 내부 만료 / 저장 실패 Rollback |
| Ch5. 예약·정산 확인 | 사장님 | 부분 연결 | 정산 총액/목록/상세 조회는 연결됨. **"예약 현황 확인"은 백엔드 자체에 참여 인원·예약 상태를 조회하는 API가 없어 미구현으로 표시**(추측으로 시나리오를 만들지 않음) |

각 사용자 행동 카드에는 다음 상태 배지 중 하나가 표시됩니다.

- **실행 가능**: 백엔드 구현과 테스트 근거가 모두 있어 전체 흐름을 재생할 수 있습니다.
- **테스트 근거 제한**: 백엔드 구현은 있지만 일부 근거(예: Controller 레벨 200
  happy-path 테스트)가 제한적입니다. Ch5의 "정산 상세 조회"가 이 상태입니다.
- **백엔드 미구현**: 백엔드 자체에 해당 기능이 없습니다. Ch5의 "예약 현황 확인"이 이
  상태이며, 실행 버튼 없이 미구현 이유만 표시합니다.

## Ch4에 보존된 기존 네 시나리오

이전 버전(단일 시나리오 탭 구조)에서 만든 결제 완료 관련 네 시나리오의 실제 데이터와
검증 근거는 삭제하지 않고 그대로 **Ch4. 결제 완료·예약 확정**의 사용자 행동으로
이동했습니다.

1. **정상 완료** — READY → PAID 전이와 CREATE/JOIN 예약 확정 분기 (토글로 전환)
2. **중복 요청** — 락 이전에 PAID를 발견하는 경우 / 두 요청이 경합해 락 안에서 PAID를
   발견하는 경우 (토글로 전환)
3. **내부 만료** — PortOne 검증은 통과했지만 락 획득 후 만료 재검증에서 거절되는 경로
   (이미 `EXPIRED`로 선점된 경로는 근거가 제한적이라 제외)
4. **저장 실패 Rollback** — Payment PAID 전이와 Reservation 저장까지 성공한 뒤
   Participant 저장이 실패해 전체가 함께 롤백되는 경로

세부 단계 데이터는 `app.js`의 `successSteps`, `duplicatePreLockSteps`,
`duplicatePostLockSteps`, `expiredSteps`, `rollbackSteps` 함수에 그대로 있으며, 각
단계가 어떤 "핵심 백엔드 흐름" 그룹에 속하는지는 같은 함수가 반환하는 `groups` 배열이
정의합니다(예: 19개 세부 단계 → 8개 핵심 그룹).

## 제외된 범위

- **정산 상세 조회**는 Controller 레벨 200 happy-path 테스트 근거가 없어 "테스트 근거
  제한"으로 표시했습니다(백엔드 구현 자체는 있어 실행은 가능합니다).
- **사장님 예약 현황(참여 인원/Reservation 상태) 확인**은 백엔드에 해당 API가 없어
  미구현으로 표시했습니다.
- **환불 실행 파이프라인** — `Refund.create(...)`/`Payment.markRefunded()`를 실제로
  호출하는 서비스 로직이 `src/main`에 없습니다(정산 조회 로직만 존재). 구현 완료처럼
  표시하지 않으며 이번 Flow Lab에도 포함하지 않았습니다.
- **Issue #36 좌석 동시성**(마지막 좌석 경쟁, 정원 초과 방지) — 아직 `develop`에
  병합되지 않았고 실행 가능한 멀티스레드 테스트도 없어 추측으로 시나리오를 만들지

- 금액/통화/소유권/외부상태 불일치 등 나머지 검증 실패 조합(Ch4 "정상 완료" 외 조합)

## 사실 / 설계 해석 / 향후 개선 구분 기준

화면과 이 문서에서 다음 세 가지를 배지로 구분합니다.

- **사실**: 기준 SHA의 실제 코드 또는 실제 테스트로 직접 확인한 동작.
- **해석**: 코드로부터 사람이 추론한 설계 의도(예: "왜 이 순서인가"). 코드 자체가 의도를
  주석으로 명시하지 않은 경우가 많아 해석임을 명확히 구분합니다.
- **개선**: 현재 구현의 제한사항과 후속 개선 후보. 아직 구현되지 않은 것을 구현된 것처럼
  표시하지 않기 위한 구분입니다.

코드 패널에는 추가로 코드 성격 배지를 사용합니다.

- **실제 코드**: 기준 SHA의 소스 코드를 그대로(또는 import 등 부수적인 줄만 생략해) 인용.
- **프레임워크 동작(코드 없음)**: BobFull 애플리케이션 코드가 아니라 Spring MVC·JPA·DB의
  표준 동작(예: HTTP 라우팅, 트랜잭션 커밋 후 락 해제)이라 별도 코드가 없는 단계.
- **의사 코드**: 현재 모든 Chapter의 코드 패널이 실제 코드 또는 코드 없음 중 하나입니다.
  향후 코드를 짧게 재구성해야 하는 단계가 생기면 이 배지를 사용해야 합니다.

## 성능·시간 관찰 영역

상세 탭의 "성능 관찰"은 각 단계를 다음 기준으로 분류해서 보여줍니다: 작업 유형(메모리
연산/DB 조회/DB 쓰기/외부 네트워크 I/O/트랜잭션 경계/락 대기 가능 구간), 트랜잭션
내부·외부 여부, DB 락 보유 여부, 쿼리 발생 여부, 외부 호출 여부, 병목 가능성.

이 값들은 `app.js`의 `derivePerformance()`가 각 단계의 `layer`/`repositoryAction`/
`externalCall`과, 그 시점까지의 누적 상태(`transactionState`, `paymentLock` 등)로부터
**파생(derive)한 분류**이며, 실제로 측정한 숫자가 아닙니다. 그래서 모든 단계에서
"실제 소요시간"은 항상 `측정 전`으로 표시되고, "측정 근거"는 항상 `코드 구조 기반
관찰(실제 측정값 아님)`으로 표시됩니다. 자동 실행의 재생 간격(약 1.4초)도 시뮬레이션
진행 속도일 뿐 실제 API 실행 시간이 아니라는 문구를 성능 관찰 탭 하단에 항상 표시합니다.

향후 실제 측정값을 연결하고 싶다면 `derivePerformance()`의 반환 객체에 `measured`,
`duration`, `p95`, `queryCount`, `lockWait`, `transactionDuration`,
`measurementSource` 필드를 그대로 사용할 수 있도록 이미 구조를 맞춰 두었습니다(현재는
`measured: false`, `duration: null`로 고정).

## 주체 기반 실행 흐름(Swimlane)

"주체 기반 실행 흐름" 영역은 사장님/일반 사용자, BobFull Backend, PortOne(외부 호출이
있는 단계에서만 표시), MySQL 네 주체 중 현재 단계와 관련된 주체만 강조합니다. 이 방향도
`app.js`의 `deriveActorTarget()`이 각 단계의 `layer`(HTTP/Response/External
Port/Repository 등)로부터 파생한 것이며, 별도로 지어낸 값이 아닙니다.

## 현재 제한사항

- "내부 만료" 시나리오는 락 안에서 만료가 재검증되는 경로만 다룹니다. 이미
  `PaymentStatus.EXPIRED`로 선점된 상태에서 완료 요청이 들어오는 경로는 실제로 코드에
  존재하지만, 이를 직접 검증하는 유닛 테스트가 없고 유일한 실행 근거가
  `BOBFULL_MYSQL_CONCURRENCY_TEST=true`일 때만 도는 env-gated 통합 테스트뿐이라 제외
  했습니다.
- "저장 실패 Rollback" 시나리오의 마지막 HTTP 응답(500)은 `GlobalExceptionHandler`의
  일반 `Exception` 처리기 코드로부터의 추론입니다. 이 정확한 실패가 컨트롤러를 통해 실제로
  500을 반환하는지를 엔드투엔드로 직접 검증하는 테스트는 확인되지 않았습니다.
- "저장 실패 Rollback" 시나리오의 실패 원인(무결성 제약 위반)은 테스트가 트랜잭션
  원자성을 검증하기 위해 의도적으로 주입한 결함입니다. 저장 대상 코드 라인 자체는 실제
  프로덕션 코드이지만, 위반을 일으키는 방식은 테스트 전용 구성입니다.
- 외부 PortOne 상태는 코드가 `paid`(boolean) 하나로만 단순화하고 있어, CANCELLED/FAILED/
  READY 등 세부 상태를 구분하는 화면 요소는 없습니다.
- Ch3(예약·결제 준비)에서는 PortOne이 호출되지 않습니다 — 백엔드는 UUID paymentId만
  발급하고, 실제 PortOne 결제창은 프론트엔드가 별도로 엽니다. 이 사실을 스윕레인에도
  PortOne 레인 자체를 표시하지 않는 방식으로 반영했습니다.
- Ch5 "예약 현황 확인"은 백엔드 미구현으로 표시했고, "정산 상세 조회"는 테스트 근거
  제한으로 표시했습니다(위 표 참고).
- 로그인(Ch1/Ch2)은 사장님/일반 사용자가 완전히 동일한 코드 경로(`POST
  /api/auth/login`)를 공유합니다 — "사장님 로그인"을 별도로 검증하는 테스트는 없으며,
  이는 로그인 로직 자체에 역할 분기가 없기 때문임을 설계 설명 탭에 명시했습니다.
- 이 화면은 기준 SHA 시점의 스냅샷입니다. `develop`이 이후 변경되면 내용이 낡을 수 있고,
  이를 자동으로 감지하는 장치는 아직 없습니다.

## 이전 구조에서 변경된 점

이전 버전은 상단에 4개의 결제 완료 시나리오 탭만 있고, 그 아래 19개(또는 4~12개) 세부
코드 카드를 한 번에 모두 나열하는 단일 레이어 구조였습니다. 이번 개편에서 다음을 바꿨습니다.

- 시나리오 탭 → **Chapter(V1 전체 사용자 여정) → 사용자 행동 → 변형(토글)** 3단계 구조로
  재편했습니다. 결제 완료는 이제 5개 Chapter 중 하나(Ch4)이며, 나머지 4개 Chapter(사장님
  준비/사용자 탐색/예약·결제 준비/예약·정산 확인)를 실제 코드 근거와 함께 새로 추가했습니다.
- 세부 코드 카드를 한 번에 모두 보여주던 "실행 단계 지도"를 **핵심 백엔드 흐름(6~9개
  큰 단계) + 접힌 세부 단계**로 재구성했습니다. 큰 단계를 클릭해야 그 안의 세부 단계가
  펼쳐집니다.
- 사장님/사용자의 **역할 기반 조작 영역**(가상 입력값 + 실행 버튼)을 추가했습니다.
- **주체 기반 실행 흐름(Swimlane)** 을 추가해 요청이 사장님/사용자 → Backend → PortOne
  → MySQL → Backend → 사장님/사용자 순으로 오가는 방향을 보여줍니다.
- 모든 초기 상태값을 같은 크기 카드로 나열하던 상태 보드를 **핵심 상태(변경된 값 위주
  3~5개) + 전체 상태 보기(접기)** 로 개편했습니다.
- **성능 관찰 탭**을 추가했습니다(실제 측정값이 없으므로 항상 "측정 전"으로 표시).
- 항상 펼쳐져 있던 4개 패널(코드/증거/설계/성능)을 **탭 전환형**으로 바꿔, 선택하지 않은
  패널은 빈 채로 계속 노출되지 않게 했습니다.
- 색상 배경을 어두운 Lab 스타일로 전환하고, 실행 전 화면에는 결과·코드가 보이지 않게
  했습니다(실행 버튼을 눌러야 첫 단계부터 시작).
